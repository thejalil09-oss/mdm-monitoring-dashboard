ABSTRACT

Mobile devices now carry corporate email, documents, and authentication tokens, but many small organisations deploy Android handsets without any visibility into their security state. A device can run with no screen lock, USB debugging enabled, and unknown-source installation allowed, and no one notices until an incident. This project built a lightweight Mobile Device Management (MDM) monitoring and compliance dashboard that runs from a standard Windows workstation using only free tools.

The system manages a fleet of two Android 13 emulators through the Android Debug Bridge (ADB). A PowerShell collector reads live device state (identity, storage, battery, installed applications, lock-screen configuration, security-patch level, and platform settings), scores each device against an eight-rule baseline mapped to the CIS Android OS Benchmark and NIST SP 800-124, and writes a structured snapshot. A static web dashboard renders that snapshot as compliance scores with per-rule evidence. An enforcement script returns devices to policy through the same ADB channel.

The baseline run found both emulators broadly non-compliant out of the box, at 45% and 25%. After applying the baseline, the managed device scored 85%. The single remaining control, disabling USB debugging, was demonstrated as a deliberate final lockdown that severs the management channel. Continuous, policy-driven monitoring of an Android fleet is feasible with open tools, and the repository is a repeatable template for auditing small fleets.

CHAPTER 1
Introduction

1.1 Background

Most employees now do a large part of their work on a phone. The same device carries corporate email, messaging, shared documents, and the app that generates the codes for two-step login. That setup is convenient for the employee and difficult for the employer. The data is no longer inside the office network, and the organisation no longer has full control over the machine that holds it.

Mobile Device Management (MDM) is the standard answer to this problem. An MDM system enrols each device, pushes a security policy to it, watches the fleet for devices that drift out of policy, and can remediate or quarantine them. The commercial products, for example Microsoft Intune, VMware Workspace ONE, and Google’s enterprise management tools, do all of this well. They also cost money, require cloud accounts, and offer far more than a small lab needs.

Android provides a cheaper management channel that ships with the Android SDK: the Android Debug Bridge (ADB). Over ADB a host can read system properties, the settings databases, the package list, and, on a debuggable build, the lock-settings database. That is enough to build a working monitoring engine without buying anything.

1.2 Problem Statement

Small organisations often put Android devices into service with no visibility into their security state. A handset can be enrolled for corporate email while it has no screen lock, USB debugging switched on, and side-loading of apps allowed. Each of these is a measurable weakness, yet without tooling nobody can answer even basic questions. How many of our devices have a lock screen? How many are encrypted? Which ones can be pulled from over a USB cable through the debug interface?

This project answers those questions for a small fleet. It builds a self-hosted, script-driven MDM monitoring and compliance dashboard for Android devices, and it demonstrates the full enforcement cycle (scan, score, remediate, re-scan) in a lab that can be rebuilt at any time.

1

1.3 Objectives

The project set out to achieve the following:

  1. Stand up a two-device Android emulator fleet, one managed and one unmanaged baseline.
  2. Write a security baseline mapped to the CIS Android OS Benchmark and NIST SP 800-124.
  3. Build a PowerShell and ADB collection engine that reads live device state and writes a structured audit snapshot.
  4. Implement a weighted compliance score with per-rule evidence.
  5. Build a browser dashboard that shows fleet compliance and per-device findings.
  6. Provide a remediation script that returns a device to policy over the same ADB channel.
  7. Compare the fleet before and after remediation and list operational recommendations.

1.4 Scope and Limitations

This is a defensive, blue-team exercise. Everything ran on local emulated devices; no physical hardware, real accounts, or production network were involved. The emulators run userdebug builds, so adbd can be elevated with adb root, which is how the probes read files a normal app cannot reach. On a production phone the same operations are normally performed by a Device Owner app, but the underlying settings are identical, so the probes transfer directly. The checks are configuration reads, not penetration tests. All credentials and identifiers in this report are synthetic.

CHAPTER 2
Literature and Tooling Review

2.1 Mobile Device Management Concepts

NIST Special Publication 800-124 Revision 2, Guidelines for Managing the Security of Mobile Devices in the Enterprise [1], is the reference framework for this work. It separates mobile security into four goals: control the device, control who uses it, control what software runs on it, and protect the data it holds. For each goal it recommends concrete controls, a screen lock, a short auto-lock timeout, full-disk or file-based encryption, application vetting, and control over developer and debugging interfaces. Every control in this project’s baseline comes from that list.

Android Enterprise distinguishes three enrolment modes: fully managed (Device Owner), work profile, and managed Google Play [5]. They differ in how much of the Device Policy Controller (DPC) API they expose. This project deliberately avoids a DPC. The emulator build is debuggable, so the enforcement layer performs the equivalent settings writes directly over ADB, using the same settings and locksettings commands the platform itself calls.

3

2.2 The CIS Android OS Benchmark

The Center for Internet Security publishes a hardening benchmark for the Android operating system [2]. The Device Access Control section (section 4) maps directly onto this project:

  • CIS 4.0. Ensure the lock screen is set with a timeout.
  • CIS 4.1. Ensure automatic lock happens within 60 seconds.
  • CIS 4.2. Ensure USB debugging is disabled.
  • CIS 4.3. Ensure secure storage (encryption) is enabled.
  • CIS 4.4 to 4.6. Ensure unknown-source installation is disabled and application verification is on.

The benchmark lists the shell command that assesses each control, usually a settings get or a dumpsys call. The probes in this project follow those commands, which is why each PASS or FAIL row in the dashboard carries the exact observed value. The output reads like an audit trail rather than a traffic-light display.

2.3 The Android Debug Bridge (ADB)

ADB is the pipe Android uses for most management tasks outside the user interface. There is a client on the workstation, a server on port 5037, and a daemon, adbd, on the device. Over an authenticated connection ADB can run a remote shell, copy files in both directions, and forward ports. On a debuggable or rooted build the shell runs with more privileges, which lets the tooling read the locksettings.db SQLite database under /data/system/. That file holds the lock state, including the credential type (lockscreen.password_type) and whether the lock screen is switched off (lockscreen.disabled) [3]. The screen-lock probe in this project reads exactly those rows.

2.4 Related Work and Tooling

Several existing systems shaped the design. Android’s Device Administration API [4] exposes policy methods such as setPasswordQuality(), setMaximumTimeToLock(), and setCameraDisabled(); the enforcement script performs the settings-level equivalent of each call. Microsoft Intune and Google’s enterprise tools are hosted versions of the dashboard built here. On the open-source side, osquery treats endpoint state as queryable data, and the Mobile Security Framework (MobSF) offers static analysis of mobile applications. None of the surveyed tools satisfied all three requirements at once: live ADB-driven collection, standards-mapped scoring, and a self-hosted dashboard. That gap is what this project fills.

3.4 Execution Steps

Seven steps were executed, in this order:

  1. Provision the environment. Install the Android command-line tools, download the API 33 system image with sdkmanager, install the AEHD hypervisor driver, and create the two AVDs with avdmanager.
  2. Boot the fleet headless. Launch both emulators with software GPU rendering (-no-window -gpu swiftshader_indirect) and confirm that adb devices lists both serials as device.
  3. Author the baseline. Write policy.json with eight controls, each carrying a severity, a weight (summing to 100), an expected state, and standard references.
  4. Collect baseline state. Run collect.ps1, which elevates adbd (adb root), queries every probe, scores each device, and writes devices.js plus a timestamped raw JSON snapshot.
  5. Visualise. Render the dashboard from the snapshot and record the initial compliance.
  6. Remediate. Run apply-policy.ps1 on the managed device to bring its settings into policy.
  7. Re-collect and compare. Re-run the collector, compare the before and after scores, and demonstrate the final lockdown (USB debugging off) and its effect on the management channel.

3.5 Compliance Scoring Model

Each rule carries a weight. A device’s score is the fraction of the total weight held by passing rules:

score = (sum of weights of PASSING rules) / (sum of weights of ALL rules) x 100

Status bands are COMPLIANT at 100%, AT RISK from 60% to 99%, and NON-COMPLIANT below 60%. The weights favour the controls with the largest practical risk reduction (lock, encryption, and the debugging interface) instead of spreading weight evenly across all eight rules. Figure 2 shows the pipeline the collector implements.

  adb devices  -->  for each serial:
       adb root          (elevate adbd)
       read identity / battery / storage / packages
       for each rule in policy.json:
          probe device  -->  observed value
          compare to expected  -->  PASS / FAIL (+ evidence)
       aggregate weights  -->  score + status
       write snapshot (JSON)  -->  dashboard
Figure 2. Compliance scoring pipeline implemented in mdm.ps1.

4.3 Collection Engine (mdm.ps1)

The module wraps ADB in thin PowerShell functions and exposes one probe per control. Two details are worth documenting because they were the practical challenges of the project.

The first is root elevation. Reading locksettings.db requires root. Enable-AdbRoot issues adb root, waits for the device to come back, then polls sys.boot_completed and the settings service until the device is genuinely ready, because adbd restarts during elevation. The second is SQLite quoting. Passing SQL that contains double quotes through adb.exe shell from Windows PowerShell mangles the command. The fix is to adb push a small .sql file to /data/local/tmp and run sqlite3 against it. The screen-lock probe therefore reads:

SELECT name, value FROM locksettings
WHERE user = 0 AND name IN
  ('lockscreen.password_type',
   'lockscreen.password_type_alternate',
   'lockscreen.disabled');

A lock credential is present when the effective password_type is non-zero and lockscreen.disabled is not 1.

4.5 Remediation (apply-policy.ps1)

Enforcement applies at the settings layer the same controls the Device Administration API would apply. The screen-lock control writes the credential-type rows directly into locksettings.db, the equivalent of setPasswordQuality(KEYGUARD_QUALITY_NUMERIC). A -DryRun switch prints every action without executing it, and -KeepAdb skips the final USB-debugging disable so a live dashboard session can continue. The full lockdown is then demonstrated as the last step. The main body of the script is:

# 1) Screen lock: write PIN-quality credential state
INSERT OR REPLACE INTO locksettings(_id,name,user,value)
  VALUES(99,'lockscreen.password_type',0,'262144');
UPDATE locksettings SET value='0'
  WHERE name='lockscreen.disabled' AND user=0;

# 2) Auto-lock timeout <= 60s (CIS 4.1)
settings put system screen_off_timeout 30000
settings put secure lock_screen_lock_after_timeout 30000

# 3) Unknown sources + verification (CIS 4.4/4.6)
settings put secure install_non_market_apps 0
settings put global verifier_verify_adb_installs 1
settings put global package_verifier_enable 1

# 4) Camera disabled (data-loss prevention)
pm disable-user --user 0 com.android.camera2

# 5) USB debugging OFF (CIS 4.2) - severs the ADB session
settings put global adb_enabled 0

4.6 Dashboard

The dashboard is a static page with no external libraries. index.html loads data/devices.js, and dashboard.js renders a fleet KPI strip (devices, compliant, at risk, non-compliant, average score), one card per device with a score ring, identity, inventory, and a per-rule evidence table, plus the policy baseline table. Because the page is static it runs anywhere, including from file://, which suits a security lab that may be air-gapped.

5.6 Final Lockdown Demonstration

As the last hardening step, USB debugging was disabled on Device B with settings put global adb_enabled 0. The effect is immediate and by design: adb devices moves the device to offline, and the management channel cannot be re-opened remotely. A device recovered from this state needs a re-enrolment (in the lab, a cold boot or wipe of the AVD). That is the correct behaviour for a hardened device, since the debugging backdoor is closed. It also confirms the operational caveat discussed in Chapter 6: an organisation should stage the USB-debugging control last, after the other controls are verified, so it never locks the administrator out mid-rollout.

CHAPTER 6
Analysis and Recommendations

6.1 What the Results Mean

The baseline run confirmed that Android devices are insecure by default from an enterprise standpoint. Both devices failed the lock-screen, auto-lock, USB-debugging, unknown-source, and verification controls. None of those failures required malicious action. They are simply the platform’s developer-friendly defaults. That is why continuous monitoring matters: settings drift or stay misconfigured, and no one notices until an incident.

The remediation result, from 45% to 85%, shows that most of the risk is cheap to remove. A handful of settings operations brought five additional controls into compliance. The remaining control, USB debugging, is inherently different. Closing it also closes the management channel, so it has to be treated as a deployment-phase decision rather than a routine remediation step.

21

6.2 Findings

  1. Out-of-box devices are broadly non-compliant. Both emulators started between 25% and 45%. Auto-lock disabled and USB debugging enabled were the most common high-weight failures.
  2. The lock screen is only trustworthy if the credential store is correct. Reading locksettings.db directly is a more reliable audit probe than dumpsys heuristics, and it is also what the platform itself consults.
  3. The security-patch level was compliant (2024-03-01) on both images. Patch currency is a build-time decision that a fleet must re-verify rather than assume.
  4. USB debugging is a switch on the management channel. Its effect, instant loss of remote visibility, is a real operational constraint for any ADB-based approach and must be scheduled deliberately.

6.3 Recommendations

  1. Stage the rollout. Apply the settings-based controls first, verify on the dashboard, then disable USB debugging as the final step with an on-site fallback, a technician with physical access who can re-enrol the device.
  2. Automate on a schedule. Run collect.ps1 periodically, for example nightly, and alert when a device’s score drops across consecutive snapshots. That catches drift instead of giving a point-in-time picture.
  3. Extend the baseline. Add the remaining CIS 4.x controls (ADB over network disabled, app restrictions, minimum password quality and length) and enterprise-specific rules such as corporate email or agent presence and certificate expiry.
  4. Move to a real Device Owner enrolment in production. The ADB channel proves the concept and is fine for a lab, but a production fleet should be enrolled as Device Owner so enforcement is cryptographic and survives reboot without a debug channel.
  5. Harden the collector host. The workstation holding adb is itself a privileged endpoint. Restrict it, keep it patched, and never store production credentials in the scripts.
  6. Keep the evidence model. Every compliance decision should continue to carry the observed value, so the dashboard stays defensible as an audit artefact.
22

6.4 Threats to Validity

The fleet consists of emulator builds (userdebug, rootable) rather than production devices, so the results reflect the emulator image and are representative of the platform behaviour, not of every vendor skin. The compliance checks are configuration probes, not security tests; a device can pass every check here and still be compromised by a determined attacker. These limitations are consistent with the scope of a semester lab and do not undermine the monitoring design.

CHAPTER 7
Conclusion

This project built a working Mobile Device Management monitoring and compliance dashboard for an Android device fleet using only the Android Debug Bridge and open tooling. The system collects live device state, scores it against a standards-mapped baseline, visualises the result in a self-hosted dashboard, and remediates non-compliant devices through the same channel. The work demonstrated three things: default Android devices are broadly non-compliant out of the box, most of the risk can be removed with simple settings-level controls, and the final control, USB debugging, carries a deliberate operational trade-off that has to be managed as part of the deployment plan.

The deliverables, the collection and enforcement scripts, the policy baseline, the dashboard, and the audit snapshots, are published in the accompanying GitHub repository and form a reusable template for monitoring Android devices in a small enterprise. The clearest direction for future work is to move the proof-of-concept from ADB to a real Device Owner enrolment, so that enforcement is cryptographic and survives reboot, while keeping the same dashboard as the single view over the fleet.
